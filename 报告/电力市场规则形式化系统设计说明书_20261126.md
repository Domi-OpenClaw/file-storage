## 1. 背景与问题

### 1.1 业务场景

朗新科技在能源互联网可信数据空间业务中，需要为各省虚拟电厂、独立储能、电力零售等市场场景提供规则解析、方案设计和客户交付。核心资产是各省发改委/能源局发布的**电力市场政策规则**。

### 1.2 现状痛点

| 痛点 | 具体表现 | 后果 |
|------|---------|------|
| **参数对不上** | 同一参数（如储能容量电价）在不同报告里数值不一致 | 客户不信任，售前交付质量不可控 |
| **无法追溯** | 客户问"这个数字哪来的"，要翻几篇报告才找到出处 | 交付物不专业，影响信任 |
| **政策过期无人知** | 政策文件过了有效期，仍被当作正式依据使用 | 可能给出错误结论，风险不可控 |
| **政策改后重做** | 一份政策修订，所有相关报告都要人工重新做 | 重复劳动，效率低 |
| **AI 解析不可验证** | AI 读政策出的结论，无法判断对错 | 没有验收标准，质量不可控 |

### 1.3 根因分析

传统产出是**给人读的 Markdown 报告**——没有机器校验、无可执行语义、规则与文档强耦合。

**解决方案**：把政策规则转成**机器可校验、可执行的结构化文档**，实现「AI 产出 + 自动验收」闭环。

## 2. 设计目标

### 2.1 核心目标

> **让政策像代码一样被编译、被测试、被追溯。**

### 2.2 五项能力

| # | 能力 | 说明 |
|---|------|------|
| 1 | **可机读** | 规则转成 JSON，参数/条款/表达式/溯源文号全结构化 |
| 2 | **可校验** | 机器自动检查结构、表达式、参数冲突、量纲异常 |
| 3 | **可执行** | 编译成可执行的 Python 函数，直接输入业务数据算结果 |
| 4 | **可追溯** | 每个数值都能追到文号 + 条款号 + 原文摘录 |
| 5 | **管时效** | 自动判定文件是否生效/过期/被替代，不靠人记 |

### 2.3 非目标

- 不是做一套完整的电力交易系统（只负责规则层）
- 不是替代政策文件本身（原文仍是权威来源）
- 不是通用规则引擎（专为电力市场场景设计）

## 4. DSL 设计（领域特定语言）

### 4.1 什么是 DSL

DSL（Domain-Specific Language，领域特定语言）是专门为某一领域设计的小语言。类比 Excel 公式 `=SUM(A1:A10)`——不用学 Python 就能算，但只能做计算。

我们的 DSL 专为**电力市场政策规则**设计，用 JSON 描述，表达式语法是 Python/JavaScript 的子集。

### 4.2 文档结构

```json
{
  "rule_id": "hb-storage-tou-2025",
  "version": "2025.1.0",
  "title": "河北省独立储能先行先试电价政策",
  "jurisdiction": {"province": "河北省", "market_stage": "storage"},
  "effective_date": "2025-03-25",
  "expires_date": "2026-12-31",

  "validity": {
    "status": "effective",
    "valid_from": "2025-03-25",
    "valid_to": "2026-12-31",
    "superseded_by": [],
    "note": "容量电价执行期 2025.1.1—2026.12.31"
  },

  "source_documents": [
    {
      "doc_no": "冀发改能价〔2025〕366号",
      "title": "关于完善独立储能先行先试电价政策有关事项的通知",
      "issuer": "河北省发展和改革委员会",
      "issue_date": "2025-03-25",
      "url": "https://..."
    }
  ],

  "parameters": [
    {
      "id": "capacity_price_annual",
      "label": "年度容量电价",
      "value": 100,
      "unit": "元/千瓦",
      "source": {"doc_no": "冀发改能价〔2025〕366号", "article_ref": "容量电价激励机制"}
    }
  ],

  "clauses": [
    {
      "clause_id": "violation-penalty-tier",
      "kind": "penalty",
      "statement": "月内违规 2 次扣减 10%；3 次扣减 50%；4 次及以上扣减 100%。",
      "expr": "violations >= 4 ? 1.0 : (violations >= 3 ? 0.5 : (violations >= 2 ? 0.1 : 0.0))",
      "inputs": ["violations"],
      "source": {
        "doc_no": "冀发改能价〔2025〕366号",
        "article_ref": "考核机制",
        "quote": "2次扣减当月容量电费的10%；3次扣减50%；4次及以上扣减100%"
      }
    }
  ]
}
```

### 4.3 条款分类（kind）

| kind | 用途 | 例子 |
|------|------|------|
| `scope` | 适用范围/准入门槛 | 容量≥10万千瓦，连续运行≥2小时 |
| `threshold` | 阈值判定 | 偏差率±5%免考核 |
| `price` | 价格/费率 | 容量电价 100 元/千瓦·年 |
| `time_of_use` | 分时时段 | 峰谷时段划分 |
| `formula` | 结算公式 | 容量认定公式 |
| `penalty` | 考核/扣减 | 违规阶梯扣减 |
| `exemption` | 豁免 | 充电电量不承担输配电价 |
| `procedure` | 流程/分摊 | 容量电费按月分摊 |
| `constraint` | 约束条件 | 年调用≥330次 |

### 4.4 表达式语法

支持算术、比较、逻辑、三元、列表、推导式，最终编译为 Python 代码。

```
算术     + - * / % **
比较     == != < <= > >=
逻辑     and or not
三元     cond ? a : b
成员     x in ['a', 'b']
列表     [1, 2, 3]
推导式   sum(d.v for d in rows)
函数     min max abs floor ceil round sum clamp
```

### 4.5 核心纪律

1. **变量必须声明**：未声明的变量直接报错，绝不默认 0（避免"静默算错"）
2. **source.quote 必须来自原文**：逐字引用，不得改写数值
3. **抓不到的条款不写进 DSL**：宁可缺，不可编
4. **每个数值都要能追到文号 + 条款号**

## 5. 时效性治理体系

### 5.1 为什么需要

「规则写对了但文件已失效」比写错更危险——前者会静默地给出错误答案。

### 5.2 四元组声明

每份规则文档必须声明：

```json
"validity": {
  "status": "effective",      // 状态
  "valid_from": "2025-03-25", // 生效日期
  "valid_to": "2026-12-31",   // 失效日期
  "superseded_by": [],         // 替代文件文号
  "note": "备注说明"
}
```

### 5.3 五种状态

| 状态 | 含义 | 能否作正式依据 |
|------|------|---------------|
| `effective` | 正式生效 | ✅ 是 |
| `trial` | 试行 | ⚠️ 可参考，不宜作唯一依据 |
| `draft` | 征求意见稿/未定稿 | ❌ 否 |
| `expired` | 已过有效期 | ❌ 否 |
| `superseded` | 已被替代 | ❌ 否 |

### 5.4 三条硬纪律

1. **缺 `validity` 声明 = 默认按 draft 处理**——「不确定」不能当成「确定」
2. **status 与日期必须自洽**：标 `effective` 但 `valid_to` 已过 → 校验器报错
3. **替代链不得断**：`superseded_by` 指向的文件必须在 source_documents 中登记

### 5.5 评估基准日可注入

支持注入任意日期作为评估基准，用于回答「**当时**这份文件能不能用」，支持历史结论的回测复盘。

## 6. 工具链与工程实现

### 6.1 目录结构

```
power-rule-dsl/
├── schema/power-rule.schema.json     # 对外契约（字段约束的权威定义）
├── src/rule_dsl/
│   ├── expr.py         # 表达式引擎：词法 → Pratt 语法分析 → AST → 求值
│   ├── model.py        # 文档模型 + 结构校验
│   ├── compiler.py     # DSL → 可执行 Python 结算函数
│   ├── validator.py    # 规则级校验（单文件 + 跨文件冲突检测）
│   └── validity.py     # 时效性治理（生效/试行/失效/替代链）
├── tools/
│   ├── dsl_cli.py      # 命令行入口（validate/eval/compile/validity/show）
│   ├── policy_ingest.py # 政策原文 → DSL 骨架批量转换
│   ├── policy_stamp.py  # 时效判定回写到原文头部
│   └── validity_report.py # 时效性自证报告生成
├── examples/
│   ├── hb-storage-tou-2025.json   # 已完整形式化的样例
│   └── incoming/                  # 批量骨架（待人工补 expr）
└── SKILL.md                        # 河图 skill 入口
```

### 6.2 核心模块

| 模块 | 代码量 | 职责 |
|------|--------|------|
| expr.py | 529 行 | Pratt 解析器、AST、求值器、NaN 检查 |
| model.py | 384 行 | 文档模型、JSON Schema 校验、数据加载 |
| compiler.py | 197 行 | 条款函数编译、签名生成、溯源注入 |
| validator.py | 240 行 | 结构校验、参数冲突、量纲异常、覆盖度 |
| validity.py | 228 行 | 时效判定、跨文档替代链、总览报告 |
| **合计** | **1,578 行** | 纯 Python stdlib，无第三方依赖 |

### 6.3 校验能力

| 检查项 | 级别 | 说明 |
|--------|------|------|
| SCHEMA | error | 必填字段、格式、枚举值 |
| EXPR_PARSE | error | 表达式解析失败 |
| UNDECLARED_INPUT | error | 输入变量未声明 |
| PARAM_CONFLICT | error | 同省同类同名参数取值冲突 |
| PRICE_OUTLIER | error | 电价量纲异常（如 3500 元/kWh） |
| VALIDITY_EXPIRED | error | 文件已过期 |
| DRAFT_STATUS | error | 文件为征求意见稿 |
| DEAD_STATUS | error | 文件已失效/被替代 |
| VALIDITY_MISSING | warning | 未声明时效性 |
| NO_ARTICLE_REF | warning | 缺条款号定位 |
| TRIAL_STATUS | warning | 文件为试行 |

### 6.4 编译产物

每个条款编译为独立 Python 函数，源码内嵌溯源注释：

```python
# 源自: 冀发改能价〔2025〕366号 / 考核机制
# 原文: "2次扣减当月容量电费的10%；3次扣减50%；4次及以上扣减100%"
def clause_violation_penalty_tier(ctx):
    violations = ctx['violations']
    return 1.0 if violations >= 4 else (0.5 if violations >= 3 else (0.1 if violations >= 2 else 0.0))
```

## 7. 数据流程与工作流

### 7.1 从政策原文到可执行函数

```
1. 采集原文 ─→ knowledge/政策规则库/<区域>/<文号>_<标题>.md
2. 批量骨架 ─→ policy_ingest.py 生成 incoming/*.json
3. 补全     ─→ 填 expr / source.quote / article_ref / validity
4. 校验     ─→ dsl_cli validate（error 必须清零）
5. 时效体检 ─→ dsl_cli validity（确认哪些可作正式依据）
6. 回写     ─→ policy_stamp.py 把时效标记写回原文
7. 编译     ─→ dsl_cli compile，产出可执行函数
8. 单测     ─→ 用真实业务数据验证条款函数结果
```

### 7.2 自动化流程

```
每周：增量采集各省新政策 ─→ 自动生成 DSL 骨架 ─→ 等待人工补全
每天：时效体检 ─→ 过期/变更自动发告警到钉钉
交付前：时效性自证报告 ─→ 客户交付物附带时效说明
```

## 8. 与洛书/河图的集成方案

### 8.1 集成架构

```
洛书知识服务平台（前店）
  ↑ 路由 / 用户接入 / 积分计量
河图生成的「电力规则计算 Agent」（引擎）
  ↑ 内置 skill：power-rule-dsl
DSL 规则库（JSON）+ 政策原文（Markdown）
```

### 8.2 各层职责

| 层 | 平台 | 职责 |
|---|------|------|
| **前店** | 洛书 | 知识检索、用户问答、Agent 接入、积分计量、分账报表 |
| **引擎** | 河图 Agent | 加载 skill，调用 compile/eval/validate/validity |
| **数据** | 规则库 | 42 份 JSON 规则 + 46 份带时效标记的政策原文 |

### 8.3 集成步骤

1. **skill 适配**：将 `power-rule-dsl/src/rule_dsl/` 按河图 skill 规范打包
2. **Agent 生成**：河图创建 Agent，挂 skill，端到端测试
3. **接入洛书**：洛书配置第三方 Agent 接入，路由到该 Agent
4. **全链路验证**：洛书前端提问 → Agent 调 DSL 引擎 → 返回带文号答案
5. **自动化**：增量采集 + 时效监控 cron 挂上

### 8.4 技术要点

- skill 规范与河图一致（入口文件、函数签名、依赖约束）
- 纯 Python stdlib 实现，无第三方依赖，部署轻量
- 规则库更新热加载，无需重启服务
- 洛书自动计量调用积分，自带运营闭环

## 附录

### A. 关键设计决策

1. **为什么不用现成规则引擎**：Java 生态太重、OPA 偏权限策略、JSON Schema 无法表达计算逻辑。折中方案是用 Python 子集 + 编译器，轻量且可控。
2. **为什么默认 draft 而非 effective**：「不确定」不能当成「确定」。默认「有效」是危险默认。
3. **为什么过期不删只降级**：历史结论仍需追溯依据，删除会断掉审计链。
4. **为什么时效标记要回写到原文**：解决「人能读层」与「机器校验层」漂移——只在 DSL 里标的话，人读原文件看不到「已过期」。
